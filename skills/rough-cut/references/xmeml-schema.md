# XMEML (Final Cut Pro 7 XML): schema used by rough-cut

This is the **only** timeline exchange format that Premiere Pro imports natively. Modern FCPXML (Final Cut
Pro X, `.fcpxml` 1.x) is refused: see the last section.

Generated by `scripts/build_premiere_xml.py`, extension `.xml`.

## Generated skeleton

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE xmeml>
<xmeml version="5">
  <sequence id="Derush_v1">
    <name>Derush_v1</name>
    <duration>2985</duration>            <!-- sum of the KEEP intervals, not the clip duration -->
    <rate><timebase>25</timebase><ntsc>FALSE</ntsc></rate>
    <in>-1</in><out>-1</out>
    <timecode>
      <rate><timebase>25</timebase><ntsc>FALSE</ntsc></rate>
      <string>00:00:00:00</string><frame>0</frame><displayformat>NDF</displayformat>
    </timecode>
    <media>
      <video>
        <format><samplecharacteristics>...width/height/pixelaspectratio...</samplecharacteristics></format>
        <track>
          <clipitem id="clipitem-v-000">...</clipitem>
          <clipitem id="clipitem-v-001">...</clipitem>
          <enabled>TRUE</enabled><locked>FALSE</locked>
        </track>
      </video>
      <audio>
        <format><samplecharacteristics><depth>16</depth><samplerate>48000</samplerate></samplecharacteristics></format>
        <track>...one track per channel...</track>
      </audio>
    </media>
    <marker>
      <comment>DOUBT false_start (conf 0.72): ...</comment>
      <name>Doubt</name><in>412</in><out>431</out>
    </marker>
  </sequence>
</xmeml>
```

No `<resources>`, no `<library>`, no `<project>`: `<sequence>` sits directly under the root.

## Timecodes: whole frames

XMEML uses no rationals. Everything is in **whole frames**, relative to the sequence `timebase`.

```python
# ntsc == "FALSE"
frames = round(seconds * timebase)
# ntsc == "TRUE"  (the real fps is timebase * 1000 / 1001)
frames = round(seconds * timebase * 1000 / 1001)
```

Mapping fps to (timebase, ntsc):

| source fps | timebase | ntsc |
|---|---|---|
| 25/1, 24/1, 30/1, 50/1, 60/1 | round(fps) | FALSE |
| 30000/1001 (29.97) | 30 | TRUE |
| 24000/1001 (23.976) | 24 | TRUE |
| 60000/1001 (59.94) | 60 | TRUE |

`displayformat` is `NDF` when ntsc=FALSE, `DF` otherwise.

## Spine: cuts are REMOVED, not deactivated

There is no spine in the FCPXML sense: the timeline is simulated with parallel `<track>` elements (1 video + 1
audio per channel) carrying the **same** clipitems at the same positions.

`build_spine_clips()` builds the list of intervals to keep by **subtracting** the `disable` cuts. A cut passage
therefore appears in no clipitem: it does not exist in the file. The remaining clips are laid end to end, with no gap.

Consequence for the duration: the `<sequence>` `<duration>` = sum of the kept intervals, **strictly less than**
the clip duration. That is normal and intended.

Four positions not to confuse in a `<clipitem>`:

- `<in>` / `<out>`: boundaries in the **source** (the clip), in frames.
- `<start>` / `<end>`: position in the **sequence** (the generated timeline), in frames. Increasing and continuous: the sequence offset is re-accumulated clip by clip, it does not follow the source timecodes.

`<enabled>TRUE|FALSE</enabled>` exists in the format (the XMEML equivalent of a deactivated clip), but the skill
does not use it: every emitted clipitem is `TRUE`. Grayed-out deactivated clips were explicitly rejected on usability grounds.

Rounding rules that keep the import valid (checked by the script before it writes): accumulate sequence
positions in whole frames (start = running total; end = running total + (out - in)); drop clips shorter than
0.07 s; never leave a leftover under one frame at the end of the clip (a clip with in == out is refused by
Premiere: "Start/end of the track item is not valid").

## Markers

Markers are placed at `<sequence>` level, never inside the clipitem, with `<in>`/`<out>` in **absolute sequence
frames**. Since the timeline was compacted, a marker's offset is recomputed by accumulating the durations of the
preceding kept clips: the source timecode cannot be used as is.

```xml
<marker>
  <comment>DOUBT repetition (conf 0.71): "I wanted" repeated at 1.2 s</comment>
  <name>Doubt</name>
  <in>412</in>
  <out>431</out>
</marker>
```

XMEML has no color attribute or `completed`. In Premiere they arrive as standard sequence markers; the
`<comment>` is readable in the Markers panel.

## File reference

A single media item. The **first** clipitem carries a complete `<file id="file-1">` (name, pathurl, rate,
duration, media/video, media/audio); all the following ones carry only `<file id="file-1"/>`. Repeating the full
block on every clipitem makes the clip import N times into the project.

`pathurl` has the form `file://localhost/absolute/path/percent-encoded.mp4` (not `file:///`). Premiere relinks
automatically if the path exists; if the clip has moved, relink by hand.

## Testing an XML without Premiere

```bash
xmllint --noout /path/clip_Derush_v1.xml
```

```bash
xmllint --xpath "count(//clipitem)" /path/clip_Derush_v1.xml
```

```bash
xmllint --xpath "count(//marker)" /path/clip_Derush_v1.xml
```

```bash
xmllint --xpath "string(/xmeml/sequence/duration)" /path/clip_Derush_v1.xml
```

Check that the `<start>`/`<end>` of the video track are contiguous (no gap, no overlap):

```bash
xmllint --xpath "//media/video/track/clipitem/start/text()|//media/video/track/clipitem/end/text()" /path/clip_Derush_v1.xml
```

## Why not FCPXML

Premiere Pro **does not read** `.fcpxml` (Final Cut Pro X, FCPXML 1.x). Tested on an FCPXML 1.10 conforming to
Apple's spec: import refused (file grayed out in the picker, and forced through "All files" the import fails or
produces an empty sequence). Adobe has never implemented FCPXML support since FCP 1.8+; the workarounds are paid
(XtoCC, SendToX) or go through DaVinci Resolve with AAF.

The kit writes no FCPXML. DaVinci Resolve 18+ and Final Cut Pro X read it natively, if you ever need that output.
